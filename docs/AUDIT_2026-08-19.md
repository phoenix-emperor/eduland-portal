# Codebase Audit — 2026-08-19

## Scope and method

This review covered the Next.js route/layout structure, shared dashboard UI,
server actions, authentication helpers, Supabase client boundaries, generated
database contract, and SQL migrations. It was a source review; it did not
alter application or database authorization logic.

## Finding requiring approval before remediation

### Critical — profile self-update policy permits privilege changes

**Location:** `supabase/migrations/20260810180446_remote_schema.sql`, policy
`profiles_update_self`.

The policy permits an authenticated user to update their own `profiles` row
using only `id = auth.uid()`. It does not restrict sensitive columns such as
`role`, `school_id`, `is_disabled`, or `must_change_password`. Because the
Supabase anon key is intentionally available to browser clients, a signed-in
user can directly call the database API and update permitted columns on their
own profile without using the application UI.

**Impact:** A user may be able to self-promote to an administrative role and
gain access to protected administrative data and actions. It may also allow a
user to alter profile-side account-status flags.

**Recommended remediation:** Add a new migration that removes or narrows the
self-update policy. The policy should allow only explicitly safe profile fields
(for example, a display name or avatar, if self-service editing is required)
and must reject changes to role, school membership, disabled status, and
password-change status. Enforce this at the database level with a restrictive
`WITH CHECK` policy and/or a controlled security-definer function. Test the
policy with parent, teacher, admin, and super-admin accounts before deployment.

No database policy change was made because it would change authorization logic
and requires owner approval.

## Maintenance findings

### High — database type safety is broadly bypassed

Many Supabase calls use `as any`, especially in
`app/dashboard/admin/actions.ts` and server-side data loaders. This suppresses
compile-time validation of table columns and result shapes, increasing the
chance that a schema change becomes a production data bug.

**Recommendation:** Regenerate `lib/types/database.ts` from the live schema,
then replace `as any` incrementally with the generated query types and small,
named view-model mappers. This is a refactor and should be scheduled separately
from the authorization fix.

### Medium — the configured lint command does not work on Next.js 16

`package.json` defines `lint` as `next lint`, but Next.js 16 no longer exposes
that command. `npm run lint` fails before linting the project.

**Recommendation:** Replace it with an ESLint 9-compatible command and add a
CI check. This requires a tooling/configuration decision, so it was not changed
in this review.

### Medium — report pages perform per-student follow-up queries

The parent history/current-report and admin-report pages enrich each student
with related data (including teacher assignments and signed photo URLs). For
large classes this creates an N+1 query pattern and can slow report rendering.

**Recommendation:** Batch related data by class, term, and subject; map it in
memory; and generate signed URLs only for report rows currently being viewed.
Validate report output carefully before changing this data-loading logic.

## Positive controls observed

- Privileged Supabase service-role access is isolated in
  `lib/supabase/admin.ts` and its header explicitly warns against client use.
- Dashboard layouts and Server Actions call `requireRole`; browser navigation
  is not treated as the authorization boundary.
- Most write actions scope records to the actor’s school and database RLS is
  enabled for the principal application tables.
- Admin account-management actions include explicit guards around Super Admin
  creation, editing, deletion, disabling, and password resets.
- Teacher score, attendance, and comment actions include server-side role and
  input-range validation.
